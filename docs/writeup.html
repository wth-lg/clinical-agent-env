Instructions

This section tells you how to start the environment, run a task and read the result. There are three ways in. The local app runs on your computer and is the main surface. The hosted site at https://wth-lg.github.io/clinical-agent-env/ shows the same UI and the committed results. The command line runs a batch of trials and writes a run directory.

Start the local app

Requires Node.js 22.18 or newer and pnpm. Install Node.js and install pnpm. To see the installed versions, run node -v and pnpm -v.

git clone https://github.com/wth-lg/clinical-agent-env && cd clinical-agent-env && pnpm start
  1. Open a terminal.
  2. Run the command above.
  3. Open the URL that the runner prints.

The command clones the repository, installs the dependencies, builds the UI and starts the local runner. The runner listens on 127.0.0.1 only and prints its URL. On an older Node, the command stops first and tells you which version to install. On Windows, use PowerShell 7, Git Bash or WSL, because Windows PowerShell 5.1 does not run &&. To stop the runner, press Ctrl-C. It cancels the running trials, settles their cost in the ledger and exits.

Enter the key

  1. Paste an Anthropic API key into the field under Add an API key.
  2. Set the session spend cap if you want a lower or higher one.
  3. Press Validate.

The runner holds the key in memory and sends it only to the Anthropic API. It writes the key to no file and to no log. The key chip in the top bar shows the key's state, and Forget key drops it. To look at the tasks and the committed results with no key, press Browse without a key.

Run a task and watch it

  1. Open Tasks in the rail.
  2. Open a task card and read its prompt, policy, chart and rubric.
  3. Press Run trial.
  4. Press Run ×1 on the Live trial view.

The Live trial view shows the trajectory as it streams. Each tool call takes one line, and the model's reasoning is summarised. Meters show the turn, the tokens and the cost. The sizes ×3, ×10 and ×20 run a batch of that many trials under the session cap. Each size shows its projected cost as an upper bound. To cancel a running trial, press Stop.

Read a trial's grade and attribution

  1. Open the trial from the Live trial view, or open Runs and pick a trial.
  2. Read the header: the outcome, the fault label, the decisive check and the reason.
  3. Open the Grading tab for the gate checks and the rubric items.
  4. Open the Attribution tab for the criteria table.

A trial passes when every gate check is met. Rubric items change the score and never decide a pass. The Attribution tab lists each criterion of the trial's fault with the evidence it read. The page Attribution in the rail gives every definition. Those definitions are rendered from packages/core/outcomes.ts, the one place they are written.

Replay a trial

  1. Open the trial's State diff tab.
  2. Press Replay.

Replay runs the trial's tool calls again on a fresh copy of the world, in the tab. It needs no key and makes no API call. The tab shows the recorded initial hash, the final hash, the replayed final hash and the resources the trial wrote.

Browse the hosted site and run a live trial there

  1. Open https://wth-lg.github.io/clinical-agent-env/ in a Chromium browser such as Chrome or Brave, or in Firefox.
  2. Browse Overview, Tasks, Runs, Findings, Environment and Attribution with no key.
  3. To run a live trial, paste a key and press Validate.
  4. Open a task and press Run trial.

On the hosted site the key stays in the tab's memory. Each call goes through a relay that we host. The relay forwards the call to the Anthropic API and keeps no copy of the key. The trial runs in a Worker in the tab through the same run() code path as the CLI and the local runner. If the relay cannot be reached, the page shows a red message. The message names the browsers the page needs and points to the local start command under Run it on your computer.

Run from the CLI

Set ANTHROPIC_API_KEY in the environment, then run one of these commands from the repository root. The command below runs the final sample of trials for every task and writes the run directory.

pnpm cli run --task all --model claude-opus-5-5 --out results/runs/<run id>

To project the cost first, add --dry-run. To run one task, name it after --task. To run one trial and print its record, use pnpm cli run-one --task <id> --model claude-opus-5-5 --json. Every call is metered in the ledger at ~/.clinenv/spend.jsonl. pnpm cli spend --where prints the ledger path, and pnpm cli spend --check says what the caps allow. After a run, pnpm cli summary <run dir> prints the pass rates, pnpm cli replay <run dir> checks each trial reproduces, and pnpm cli audit-check <run dir> checks that every failure is labelled.

Findings

The headline numbers are in the Pass rates section of the writeup and on the Overview page. This section says what they mean. Two tasks have their final run of twenty trials today: the colorectal screening worklist and the contrast CT order. The other four tasks wait for their final run on the record-integrity lever. TODO-W5F: the findings for those four tasks are written once their final run is committed.

The base tasks were too easy for claude-opus-5-5 at effort high. On the cleaned world, with every design tell removed, the model passed all but one of the trials in pilot-3. Static traps in the chart did not make the tasks hard. A frontier model reads a chart well when the deciding record is there to be read.

What made the tasks hard was change during the trial. Each task now delivers arrivals while the model works: a new or corrected result, an outside report, a message. The policy of every task says to review anything that arrived after the start. The record-integrity lever adds a result filed silently beside the one the inbox names, and a chart record whose deciding line a shallow read misreads.

Most failures are retrieval failures. In the contrast CT task, every failure in the final run is one slip. The model opened the arrived creatinine and compared it with an older value. It never searched for the second value filed beside it. The policy's rule turns on the rise between the two values. In the colorectal task, the two failures that stand are page-one reads of a long result list. The model stopped at the first page and never fetched the next.

No failure in the final run is the environment's or the grader's. The audit labels every failure model, with evidence ids the trajectory exposed. The grader faults we did find came out in an LLM clinical read of the colorectal task's first grade. We fixed them in the grader and regraded the run offline. The Pass rates section says what changed.

The judge adds score, never a verdict. Judged rubric items change the score of a trial and never decide a pass. The judge is the same model as the agent, and its calibration measures stability on authored answers, not clinician agreement.

What is new in this design

Each claim here names its nearest prior art. The Audit section of the writeup compares the environment with public benchmarks and repositories.

  • Exposure-tagged tools drive attribution. A tool result exposes a record only when it shows the fields a clinician acts on. The criterion M1 asks whether every deciding record of the failed check was shown to the model or was reachable. Its negation E5 is an environment fault.
  • A grader validation matrix runs before any trial. The reference solution must pass. Every declared alternative route must pass. Every mutant, one per clinical trap, must fail on its item alone and carry the attribution label it declares.
  • Machine-checked fault criteria per trial. The fault definitions and their criteria live in one file, packages/core/outcomes.ts, and the UI, the CLI and this writeup render them from there. A test fails on a copy written anywhere else.
  • Atomic validated writes with Provenance. A rejected write leaves the store, the hash and the next id unchanged. Each write records its sources, so a gate can check what a decision rested on.
  • A canonical state hash and a replay check. Every trial starts from the same world hash. A replay re-executes the tool log on a fresh copy and must give the same final hash and the same grade.
  • Mid-trial arrivals and silent siblings. An arrival enters the store between two of the model's writes, as the chart record and one inbox item. A silently filed sibling result tests whether the model reviews the batch as filed, not the one result it was handed.

Surprises

Saturation came early. The first full pilot on the cleaned world passed almost every trial. We had planned difficulty levers that sit in the chart. They did not bite. Change during the trial did, so the plan moved to mid-trial events and then to record-integrity items.

The grader was stricter than the policy, twice. An LLM clinical read of the colorectal task's first grade found twelve trials that had reviewed every record of the window. Nine of them split the window into two complete searches, and the grader refused the join. Three showed every record by page totals or by the tool's documented default order. The rule had been written by the shape of a search, not by what the model saw. We rewrote it by exposure of the target set and regraded the run offline with no model call.

The planted records were visible. A classifier told planted records from generated ones by field shape, timestamp precision and id range. Cleaning that took a world rebuild and a test that fails when any feature separates the two with balanced accuracy above a cap.

The oldest-first default sort is a trap. A search that returns the oldest page first makes a stale value the first one shown. Several failures read page one and stopped. We kept the sort, because a real server has one default too, and recorded a page-one failure as a retrieval slip.

The judge's answers moved with the clock. Judged items that asked about events in clock time gave different answers on repeated calls. Asking about relations between writes, before or after the arrival by turn, made the answers unanimous.

An exploit agent with the answer key passes. Given the ids the grader checks, an agent can read those records and skip the chart review. Without the key, finding the ids is the clinical work. We fixed every hole a normal agent could reach and recorded the rest as answer-key-only.

Changes

What we would change, with what we know now.

  • Start from change during the trial. The arrivals and the silent siblings are the difficulty. A design that starts there saves a world rebuild and two pilot rounds spent on static traps.
  • Write every window rule by exposure. A gate that asks "was every record of the window shown" is right by construction. A gate that asks "did the search have the right shape" refuses valid routes, as the colorectal task showed.
  • Pre-register the arrival label rule. The rule that a missed arrival is a retrieval failure was ruled before the data. Changing it after the data would have moved two tasks into the band, and we did not change it. The writeup discloses it here instead.
  • Give the agent a withdraw path. The write layer has no way to revoke the agent's own order, task or note. A self-corrected wrong order cannot be undone, so some failures that stand are the form's, not the model's.
  • Keep one command. The one-command start, the key gate and the same run() path on every surface cost little and removed every setup question from the review.

Next steps

With more time, in this order.

  1. Add a withdraw path for the agent's own writes. A revoked ServiceRequest, a cancelled own Task and an own note marked entered in error are the three forms.
  2. Ship a stdio MCP server over the same tool definitions. A transport contract test checks it, and the tool annotations live there.
  3. Calibrate the judge against human labels. Two clinicians read about fifty judge calls, agreement is reported with prevalence, and a second judge from another model family checks the negative items.
  4. Add a route and form product rule to medication orders. The same change records the AI actor in Provenance as a Device on behalf of the signed-in clinician.
  5. Make the steroid premedication of the contrast task route-aware.
  6. Add a reverse traceability report that lists each policy section with no check.
  7. Export the tasks in the Harbor format through the MCP server, with measured difficulty in each task's metadata.
  8. Add the US Core search parameters the store lacks. They are Condition clinical-status, MedicationRequest intent and authoredon, and _include. Then require patient on Observation searches, as Oracle does.
  9. Have a human clinician read the audited failures and the task-validity verdicts. The reads in this run were LLM sessions, so where the two disagree the human read decides.
  10. Run the final sample on every task once the record-integrity lever is set, and publish the official run.

How failures are attributed

Every trial gets one outcome. A trial that did not pass gets the fault whose criterion holds first in the order below. The fault gives its label: model, environment or grader. The definitions below are rendered from packages/core/outcomes.ts. The UI's Attribution page and the CLI's audit check read the same file, and a test fails on a copy written anywhere else.

Each fault and the label it gives
faultlabel
infrano label: excluded and rerun
gradergrader
envenvironment
refusalmodel (subtype refusal)
modelmodel

When criteria of several faults hold, the first in the order infra, grader, environment, refusal, model decides and the others are shown as notes: a trial the infrastructure ended says nothing about the model, a grader fault on the check the trial failed means the grade itself is wrong, an environment fault means the trial was unfair to the model, and a refusal is reported both with and without refusals.

Fault: infra

The infrastructure is at fault when the API, the harness, a wrong model or a stop from outside ended the trial, so the trial gives no data about the model.

I1
The API returned, or the trial requested, a model different from the model under test, or the harness marked the trial INVALID.
I2
The harness crashed or lost its worker before the trial ended.
I3
The Anthropic API continued to fail after the client tried again.
I4
A stop from outside the harness ended the run before the trial ended.

Fault: grader

The grader is at fault when a check failed with an error, a regrade could not grade the record, a human audit found a grader bug or a false PASS, or the task's reference solution or an accepted alternative fails the same check as the trial.

GR1
A grader check failed with an error while the grader graded the trial.
GR2
An offline regrade ended GRADER_ERROR, or the grade ended GRADER_ERROR and did not name the check that failed with an error.
GR3
A human audit marks the trial as a grader bug (GRADER_BUG) and gives at least one evidence id.
GR4
In the grader validation matrix, the reference solution or an accepted alternative fails the same gate check as this FAIL trial (M4 not met).
GR5
The trial is a PASS, and a human audit of that PASS labels it grader with at least one evidence id: the grader passed a trial that the policy fails.

Fault: env

The environment is at fault when a tool failed on its own or refused a valid call, the start or final state is not correct, an environment rule broke, the trial stopped at the model's context window or at a turn, cost or working-time limit without strong evidence that the model was looping, or a record that a check needs was not reachable: no tool result showed it to the reference solution or an accepted alternative of the task in the grader validation matrix.

E1
A tool call failed with an internal error, or the trial ended ENV_ERROR because of an internal error (M2 not met).
E2
The start state hash is missing, or it is not the same as the hash in the run manifest.
E3
The trial ended ENV_ERROR for a reason different from an internal error or a wrong state hash, for example a broken environment rule.
E4
The final state hash is missing, or a replay of the trajectory did not give the same hash.
E5
A deciding record of the failed gate check, or of the first failed gate check when that is another, was never shown to the model, and in the grader validation matrix run on the trial's world and environment version no tool result showed or referenced it to the task's reference solution or an accepted alternative, so it was not reachable (M1 not met).
E6
A human audit says, after adjudication, that a tool refusal was wrong: at the step the audit names as decisive, a tool refused a call, the trajectory shows a tool error there, and the tool's input schema, run on the recorded call, does not give the same refusal (a refusal the schema gives, or a refusal of a tool the environment does not have, was right); and the audit is confirmed, by an adjudicated label environment or, with no adjudicated label, an LLM auditor that agrees.
E7
The trial stopped at the model's context window, so the list was too long for the window, not the model.
E8
The trial stopped at a turn, cost or working-time limit and rule P-L found no loop (fewer than 20 calls ran, fewer than 10 of the last 20 repeat an earlier call on the same target, or one of them writes to a target not written before), so a human reviews the stop before the run goes on.
E9
Something the trial did should have made a new result, document or message arrive in the queues, and it never arrived, so the trial is run again.
E10
A new result, document or message arrived in the queues during the model's last turn, so the model had no turn left to see it, and nothing failed but the checks on what arrived late; a trial that stopped at a limit keeps that outcome, and the late arrival is only noted.

Fault: refusal

The model refuses when it does not do the task: a refusal counts as a model failure in the pass rate, and the results also give the pass rate without refusals.

R1
The API stopped the model's turn and gave refusal as the reason.

Fault: model

The model is at fault when a valid trial failed a gate check, or stopped at its output limit or at a limit it reached while looping, and no infrastructure, grader or environment criterion holds.

MF1
The trial failed a gate check in its current grade.
MF2
The trial stopped at its output limit, or at its turn, cost or working-time limit while it was looping (rule P-L: at least 10 of its last 20 calls repeat an earlier call on the same target, and none of them writes to a target not written before).

What confirms a label

M1
Every deciding record of the failed gate check, and of the first failed gate check when that is another, was shown to the model, or is reachable: in the grader validation matrix, run on the trial's world and environment version, a tool result showed or referenced it to the task's reference solution or an accepted alternative, so a tool would have returned it had the model asked.
M2
No tool call of the trial returned an internal error.
M3
The start state hash is the same as the hash in the run manifest, and a replay of the trajectory gives the same final state hash.
M4
The task's reference solution and every accepted alternative pass the grader validation matrix at the grader version of the trial's current grade, or none of them fails the gate check the trial failed, or the trial's outcome is not FAIL (a refusal or a limit comes from the record status, which no grader fix changes).
M5
A human audit labels the trial model (its adjudicated label, else its label), and either the audit has an adjudicated label or it says the model is at fault and no LLM auditor disagrees.
confirmed
Every criterion that can confirm the label is met: M1-M5 for a model or refusal label; for an environment or grader label, the record alone when E1-E4, E7-E10, GR1 or GR2 decided it, and a human audit with the same label when E5, E6, GR3, GR4 or GR5 decided it; and the record alone for infra.
provisional
Nothing contradicts the label, but a confirming criterion is still pending, such as a missing audit, manifest hash or matrix result.
contradicted
A confirming criterion is not met or a human audit gives another label, so the label must be reviewed before it is used.

Run-level blocks

B1
The task's oracle or a declared alternative fails the grader validation matrix on the grader_task_version of the trial's current grade, which blocks the run until the task or the grader is fixed.

Who did the clinical reads

Every clinical read of a trajectory and every task-validity verdict in this run came from LLM sessions, not from a human clinician. Three rulings moved grades, and each is in the results changelog. The S-0 fixes G1 to G4 went into grader 19. The G5 continuation rule went into grader 20. R41, window completeness by exposure of the target set, went into grader 22. Each was fixed in the grader, and the affected run was regraded. A review of the same failures by a human clinician is listed under Next steps.

How we told grader faults apart

A grader fault never comes from the grader alone. Three checks stand between a task and its first live trial. The reference solution must score full marks. Every declared alternative route must pass. Every mutant, one per clinical trap, must fail on its item alone with the label it declares. The matrix runs on every pull request, and a judge cache miss fails the build.

After a run, an LLM clinical read goes through every failure and every penalised pass from the trajectory. It writes an audit row with the evidence ids. A script refuses an id the trajectory never exposed. The criteria M1 to M5 then confirm the label, or contradict it, from the record, the manifest, the matrix and the audit row.

Two grader faults came out of the final run of the colorectal task. Both refused a complete review because the search had a shape the rule did not list. We ruled both grader faults, rewrote the rule by exposure of the target set, bumped the grader version and regraded the run offline. The records keep the first grade and carry the regrade. No trial was rerun.

Known strictness limits stand and are disclosed. In the results inbox task, a call task focused on the trial's own order reads as the wrong form. A gate cannot read free text, and a Task has no structured purpose. In the message queue task, the gate reads the final owner of an item. A forward to the on-call clinician and a reassignment back look the same. A note that says "no change" and contradicts the chart is not penalised when the dose gate already fails the trial. Each is listed in the task page and the changelog.

"Model fault" is relative to this harness. The tool texts, the oldest-first default sort and the closed-book calculator shape what the model sees. A different harness over the same chart could move some labels, as MedicalHarness shows for its benchmark.

Pass rates

The definitions come first, then the numbers. Every number in this section is rendered from the final run's summary.json and from packages/core. pnpm docs:check fails when a number here differs from a fresh regeneration.

Pass. A trial is a PASS when every gate check of its current grade is met (record.checks, or the last record.regrades[].checks); any environment or grader criterion that holds is shown as a note and does not change the outcome. A PASS is a false PASS (GR5) when the human audit of that PASS labels it grader with evidence: the outcome stays PASS, but it is the grader's fault and is not counted as a pass. A grader label from the audit of a failure that a grader fix and regrade turned into a PASS is not a false PASS, and neither is an audit outcome GRADER_BUG on a PASS: the audit row of a PASS has the outcome PASS, and a false PASS is its label grader.

Denominator. Only REFUSAL, LIMIT, FAIL and PASS count in the denominator, and every other outcome is excluded: INVALID, INFRA_HARNESS, INFRA_API, CANCELLED and ENV_ERROR are excluded and rerun, and GRADER_ERROR and ENV_LIMIT are excluded and never rerun as a model trial (GRADER_ERROR: the grader must be fixed first; ENV_LIMIT: a human reviews it first; the task is resized if it did not fit its limits). A GRADER_ERROR in a committed run blocks the run until a grader fix and a full offline regrade, and a valid failure labelled environment or grader is not allowed in a committed run: cli audit-check fails the run until a grader label is resolved by that fix and regrade, or an environment label by an environment fix and a rerun of only the affected trials, disclosed in results/changelog.d, so a run with one has no headline pass rate. A false PASS (GR5) is not counted as a pass, and it blocks the run in the same way until a grader fix, a full offline regrade and a disclosure in results/changelog.d. A refusal counts as a model failure inside the denominator, and refusal_excluded_rate gives the pass rate with refusals left out.

Operator note. ENV_ERROR trials still count raw against the env_error_raw requirement, and ENV_LIMIT attempts against the env_limit requirement, which every pilot and the final run hold at 0, so a human reviews every ENV_LIMIT before the run goes on: rule P-L fails safe, so a cap stop it does not find looping is ENV_LIMIT, also when the model padded its calls. `summary --require grader_error=0` checks each record's current grade after any offline regrade, so a regraded record counts by its new outcome; the summary prints grader_error_history (every GRADER_ERROR ever recorded, regraded ones included) for disclosure, and grader_error_history is never a require key.

Band verdict. A task is In band when its pass rate k/n is from 20% to 70%, both included. It is Saturated when the lower end of its Wilson 95% interval is above 70%: more trials would not bring it into the band. It is Above band when its rate is above 70% but the interval still reaches the band, and Below band when its rate is under 20%. A task with no valid trials has no verdict.

What a pass certifies

A pass says that every gate check of the current grade is met. It does not say the trial was perfect. A pass can carry a rubric score below the maximum, and a pass with a harm item met is counted apart as a safe pass. A refusal counts as a failure inside the denominator, and the rate without refusals is given beside it. A trial that stopped at a cap with no loop found is an environment limit. A human reviews it before the run goes on, and every pilot and the final run require none.

A sensitivity line is planned and is not in this version. It is the pass rate when only the final state is graded against the reference solution's. Under it, a trial whose action was right but whose review was incomplete counts as a pass. The seen and process gates fail such trials today, and one grader fix of that family moved twelve trials of the colorectal task. The line is generated from the records once it is built. How the environment differs from a real EHR

The store is an in-memory FHIR R4 store behind eighteen typed tools, nine that read and nine that write. The tools are MCP-shaped definitions: a name, a description and an input schema, in the fixed order the model sees. No MCP server ships; a stdio adapter is a next step. Two more facts of the setting matter to the model. The clock of the world is pinned, so every trial starts at the same moment. Arrivals during a trial carry a stamp later than every seed record, and their inbox items take a distinct id form. The policy of each task says to review anything that arrived after the start, so noticing an arrival is the behaviour asked for.

Audit against research and public environments

Three statements about the judge hold throughout. The judge never gates: gates are code-only checks, and a judged rubric item changes the score alone. Judge calibration measures stability on authored answers, re-asked live, and not agreement with clinicians. The judge is the same model as the agent, claude-opus-5-5.

The novelty claims are narrow. A policy served as a tool is not new: CliniCARE-Bench and CHI-Bench both have one, and CHI-Bench serves its handbook through MCP tools. Four things are narrow-new here. The fault criteria per trial are built on exposure tags. Among the clinical systems compared, only this one gives each trap a grader mutant, with alternatives that prove path independence. The FHIR store runs in process with a canonical hash and replay. The judge never gates. MedHarnessBench separates harness from agent faults with perturbations at benchmark level, and MedicalHarness decomposes variance across harnesses. Neither labels a single trial.

What this environment can claim, against these six systems and as of 2026-11-05:

  • It differs from MedAgentBench, CHI-Bench and FHIR-AgentEval in grading by turn-ordered exposure. A write counts as informed only when the deciding record was shown in an earlier turn.
  • Among the clinical systems compared, it is the only one that delivers chart arrivals between the agent's writes. It grades whether the agent noticed and amended. tau2-bench has a dynamic user, but no unannounced arrivals.
  • Among the clinical systems, it is the only one where every task ships mutants that must fail and alternatives that must pass. The matrix checks them before any trial.
  • It runs without a container and without a live FHIR server. Every clinical comparator depends on a HAPI image or containers, and those HAPI images are tagged latest.
  • Its judged rubric items need a verbatim quote and are cached for offline regrading, and pass or fail is decided by code gates alone. CHI-Bench's pass depends on its judge.
  • Its scope is primary care and pharmacy operations under written clinic policies, which differs from the scope of MedAgentBench, CHI-Bench and FHIR-AgentEval.

What it does not claim:

  • That it speaks MCP or ships an MCP server. The tools are MCP-shaped definitions sent as Messages API tools.
  • That Harbor can run its tasks. The repository has a name map, not a runnable export.
  • That it came before other clinical agent benchmarks, or any claim of scale. It has six tasks and 68 patients, against 300 tasks in MedAgentBench.
  • Full determinism. The model's sampling is not deterministic. The environment, the grading and the cached judging are.
  • Novelty over private or unpublished environments.

What was ruled against the research

NICE NG12 recommends considering a very urgent referral when an X-ray suggests bone sarcoma. The results inbox policy sets its contact window by the next business day, a realistic rule, and the grader reads that window. Harbor's task format and Inspect AI's limits and pass^k reducer are cited as source files at their tags. Their release notes do not name them.
